    Development

    Day-to-day development workflow, code quality, testing, and connecting to deployed resources.

    Local Development

    Start the agent with uv run server. It reads .env (setup: Getting Started) and needs no containers or deployed infrastructure.

    SERVE_WEB_INTERFACE=TRUE uv run server                     # API and ADK web UI at 127.0.0.1:8000
SERVE_WEB_INTERFACE=TRUE RELOAD_AGENTS=TRUE uv run server  # Reload the agent on edits under src/
LOG_LEVEL=DEBUG uv run server                              # Debug logging

    With the service URIs in .env unset, ADK stores sessions and artifacts locally under src/<package>/.adk/ and keeps memory in-process (Environment Variables: Cloud Resources). .env is shared with Docker Compose: with the URIs set, uv run server uses the deployed services instead, and reaching the session database needs an IAP tunnel: Compose starts one, or start it yourself (Cloud Backend Options).

    RELOAD_AGENTS reloads the agent, tools, callbacks and prompt; restart the server after changing server.py, config.py, telemetry.py or .env. Local runs export traces and logs to Google Cloud like the deployed service; metrics go to Google locally only with cloud.region in OTEL_RESOURCE_ATTRIBUTES (Observability). Set OTEL_RESOURCE_ATTRIBUTES=service.namespace=<your-name> in .env so teammates can filter to your traces when reviewing experiments. Full variable reference: Environment Variables.

    Feature Branch Workflow

    # Create branch (feat/, fix/, docs/, refactor/, test/)
git checkout -b feat/your-feature-name

# Develop locally
SERVE_WEB_INTERFACE=TRUE RELOAD_AGENTS=TRUE uv run server

# Commit (Conventional Commits: 50 char title, list body); the hooks run lint/format/typecheck
git add . && git commit -m "feat: add new tool"

# Before pushing: unit tests (100% coverage) and the Postgres integration lane (needs Docker)
# Add --log-cli-level=DEBUG to any run for live logs
uv run pytest --cov
uv run pytest tests/integration

# Push and create PR
git push origin feat/your-feature-name
gh pr create  # Follow PR format: What, Why, How, Tests

# After merge to main, monitor deployment
gh run list --workflow=ci-cd.yml --limit 5
gh run view --log

    GitHub Actions automatically builds, tests, and deploys to Cloud Run. Check job summary for deployment details.

    Code Quality & Testing

    The pre-commit hooks lint, format, and type-check every commit. Run the unit tests (100% coverage required) and the integration lane before pushing, and the agent evals when agent behavior changes. The smoke lane needs a deployed service: CI runs it after each deploy, and you can run it against a deployed URL yourself (Smoke Tests).

    Standards:
    - Type Hints: Strict mypy, modern Python syntax (| unions, lowercase generics)
    - Code Style: Ruff enforced (88-char lines, Path objects, security checks)
    - Docstrings: Google-style format (args, returns, exceptions)
    - Testing: 100% coverage on production code, exclusions for configuration modules, fixtures in conftest.py, test behaviors and errors

    Pre-commit Hooks

    Pre-commit runs lint, format, type, and spelling checks as a fix-in-place git hook on every git commit. It does not run pytest. To run the Python tools by hand, the equivalent chain is uv run ruff check --fix && uv run ruff format && uv run mypy, in that order.

    CI runs the same hooks with uv run pre-commit run --all-files --show-diff-on-failure. Run uv run pre-commit run --all-files to check the whole tree the way CI does, like after changing a hook or pulling in upstream changes. In CI, any hook that would modify a file fails the job and prints the diff it would have applied.

    Coverage spans Python (ruff, mypy), Terraform (terraform fmt), GitHub Actions workflows (actionlint), the YAML/TOML/JSON config files, and spelling in every text file (codespell). codespell reads [tool.codespell] in pyproject.toml; add a word to ignore-words-list only for a confirmed false positive, with a comment saying why.

    Ruff's linter runs before its formatter. ruff check --fix can change layout (removing an else de-indents a block), and the formatter has to see that result. The fix runs only where --fix is passed explicitly; pyproject.toml deliberately does not set fix = true, so a bare ruff check reports instead of rewriting.

    terraform validate is deliberately not a hook: it needs terraform init per root, which is too slow for a commit. CI validates instead.

    Local tooling: the Terraform hook calls the terraform binary that tenv provides (a prerequisite). tenv reads .terraform-version, the same pin CI installs, so the hook formats exactly as CI does. After the pin changes, run tenv terraform install to fetch the new version. pre-commit builds actionlint itself, using the Go toolchain on PATH if there is one and otherwise downloading one into its own cache. Install shellcheck too: actionlint runs it over workflow run: scripts only when it is on PATH, so without it the hook skips that pass and its findings surface only in CI's code-quality job.

    One-time setup (writes .git/hooks/pre-commit):

    uv run pre-commit install

    Manual invocation:

    uv run pre-commit run --all-files              # All hooks on all tracked files
uv run pre-commit run --files path/to/file     # Scope to specific files
uv run pre-commit run ruff-check               # Run a single hook

    Hooks are configured in .pre-commit-config.yaml. pre-commit autoupdate is a no-op for the language: system hooks, so update those at their own source:

    Hook Version comes from Update with
    ruff, mypy, codespell uv.lock uv lock --upgrade
    terraform fmt .terraform-version, installed by setup-terraform in CI and by tenv locally (tenv provides the terraform on PATH) edit .terraform-version, then tenv terraform install
    uv-lock your installed uv, held inside required-version (CI uses its pinned setup-uv uv) uv Version
    everything else the rev in .pre-commit-config.yaml, a commit SHA with a # frozen: vX.Y.Z comment Dependabot's weekly PR, or uv run pre-commit autoupdate --freeze

    Agent Evals

    Run the deterministic agent eval gate before merging changes that touch agent behavior (instructions, tools, callbacks, model):

    uv run pytest tests/eval -m "deterministic"     # real model inference, deterministic scoring; needs Vertex creds from .env
uv run pytest tests/eval -m "deterministic" -s  # same, streaming ADK output as each run happens

    See Agent Evals for the full evaluation suite reference.

    Connect to Deployed Resources

    Run the local agent against the deployed dev session database (Cloud SQL), memory (Agent Engine) and artifact bucket. Docker Compose starts everything this needs: the app container and an IAP tunnel container that reaches Cloud SQL's private IP through the bastion host, so the app connects to localhost:5432 as on Cloud Run.

    Important

    This path needs a completed deploy and roles/iap.tunnelResourceAccessor on your Google account for the IAP tunnel. Grant it via gcloud projects add-iam-policy-binding or the GCP Console.

    1. Open the deploy run's job summary (gh run view <run-id> --web). In the deployed-resource block of .env, uncomment and fill in BASTION_INSTANCE, BASTION_ZONE, SESSION_SERVICE_URI, MEMORY_SERVICE_URI and ARTIFACT_SERVICE_URI, plus any variables you added for your own resources. Set SERVE_WEB_INTERFACE=TRUE in .env too: Compose reads only .env, not your shell. Environment Variables: Cloud Resources says where to find each value.

    2. Start the stack and leave it running:

      docker compose up --build --watch   # Stop: Ctrl+C or docker compose down

      Edits under src/ sync into the container and restart the app; changes to pyproject.toml or uv.lock rebuild the image.

    To go back to local storage, comment the service URIs out again and use uv run server. To connect uv run server to individual backends without Compose, see Cloud Backend Options. Watch mode, volumes and the tunnel: Docker Compose Workflow; image layout: Dockerfile Strategy.

    Common Tasks

    Dependencies

    # Add runtime dependency
uv add package-name

# Add dev dependency
uv add --group dev package-name

# Update all dependencies
uv lock --upgrade

# Update specific package
uv lock --upgrade-package package-name

# After updating pyproject.toml or uv.lock:
# - Locally: Restart server or Docker Compose (auto-rebuild with watch)
# - CI/CD: Commit both files together (required for --locked to pass)

    Version Bump

    When bumping version in pyproject.toml:

    # Edit version in pyproject.toml
# Then update lockfile
uv lock

# Commit both together
git add pyproject.toml uv.lock
git commit -m "chore: bump version to X.Y.Z"

    Why: CI uses uv sync --locked which will fail if lockfile is out of sync.

    Python Version

    .python-version names the interpreter. uv reads it locally, and every CI uv python install step runs without a version argument so CI reads it too. Four pins can't read the file and must match it: requires-python, ruff target-version and mypy python_version in pyproject.toml, and both FROM python:<version>-slim stages in the Dockerfile. To move versions, update those pins first (uv python pin rejects a version outside requires-python), run uv python pin X.Y, then uv lock and commit everything together. tests/unit/test_pinned_versions.py fails if any pin drifts, or if a workflow sets its own Python version.

    uv Version

    uv is pinned in two tiers:

    • Your uv: [tool.uv] required-version in pyproject.toml is a range covering one minor series (>=X.Y,<X.(Y+1)). uv refuses every project command, uv run included, when the running uv falls outside it, so any patch of that minor works locally. The uv-lock pre-commit hook runs this uv.
    • CI and the image: the Dockerfile uv image tag and the version: input on every setup-uv step hold one exact version inside that range.

    tests/unit/test_pinned_versions.py fails if the exact pins disagree, if a setup-uv step has no version:, or if required-version stops being the exact pin's minor series.

    To move uv:

    1. Check the setup-uv release pinned in the workflows: its checksum table (src/download/checksum/known-checksums.json in the action's repo, at that tag) must list the new uv. If it doesn't, move setup-uv to a release that does. Don't pass the action's checksum: input instead: it replaces the per-platform table with one string.
    2. Set the new version in the Dockerfile and every setup-uv version: input.
    3. On a minor bump, move required-version to the new minor series.
    4. Run uv run pytest tests/unit/test_pinned_versions.py, then the full suite.

    When your installed uv is outside the range and you don't want to change it, run a pinned uv ad hoc: uvx uv@X.Y.Z <command> uses the pin without touching your install.

    Custom GCP Services or IAM Roles

    Need a new GCP API or WIF IAM role for your feature? Add it to the designated main module extension points — no bootstrap re-run or admin required.

    • terraform/main/services.tf — add to the services set to enable a GCP API
    • terraform/main/iam.tf — add to the wif_additional_roles set to grant the GitHub Actions WIF principal a new role

    Add the roles or services AND the resources that use them in the same PR. The time_sleep resources handle propagation within the apply — declare depends_on on the correct sleep instance(s) for any resource that requires a newly-enabled service or role.

    See Extending the Main Module for the full pattern, code examples, and rationale.

    Model Call Timeout

    ROOT_AGENT_MODEL_TIMEOUT_MS in agent.py caps each model call the agent makes, in evals and in the deployed service. A call that exceeds it raises TimeoutError and is not retried. The limit covers the whole call, including a streamed reply, not just the time to the first token. Size it to your agent's longest legitimate model response, not its whole turn: a long-running workload may also need a longer Cloud Run request timeout, or a background task or queue instead of a synchronous request. The value travels in the agent's generate_content_config (ADK LLM agent configuration) as google-genai's HttpOptions.timeout, in milliseconds; retries are HttpRetryOptions on the same object.

    Test Deployed Service

    Proxy Cloud Run service to test locally:

    # Service name format: ${agent_name}-${environment}
gcloud run services proxy <service-name> \
  --project <project-id> \
  --region <region> \
  --port 8000

# Test
curl http://localhost:8000/health

# With web UI (if SERVE_WEB_INTERFACE=TRUE)
open http://localhost:8000

# Stop proxy: Ctrl+C

    See Cloud Run proxy documentation.

    Observability

    Server Logs:
    - Print to stdout (via LoggingPlugin callbacks)
    - Basic request/response logging for immediate feedback

    OpenTelemetry Traces and Logs:
    - Detailed traces → Cloud Trace
    - Application logs and GenAI events → Cloud Logging, correlated with traces
    - ADK metrics → Cloud Monitoring on Cloud Run (locally with cloud.region set)

    See Observability for querying, filtering, and trace analysis.

    Project Structure

    your-agent-name/
  src/your_agent_name/
    agent.py              # ADK App and LlmAgent configuration
    callbacks.py          # Agent lifecycle callbacks (logging, safety, tool augmentation)
    prompt.py             # Agent instructions (InstructionProvider pattern)
    config.py             # Typed env-var validation (Pydantic ServerEnv)
    telemetry.py          # OpenTelemetry initialization
    server.py             # FastAPI composition root (services, DI, routing)
    tools.py              # Custom FunctionTools for agent use
  tests/                  # Test suite (unit/integration/smoke/eval lanes)
    unit/conftest.py      # Unit-lane fixtures, mocks, and test env setup
    unit/test_*.py        # Default lane; modules mirror source structure
  terraform/              # Infrastructure as code
    bootstrap/{env}       # One-time CI/CD setup per environment
    main/                 # Agent cloud resource deployment
  docs/                   # Documentation
  .env.example            # Environment template
  pyproject.toml          # Project configuration
  compose.yml             # Local agent against deployed resources
  Dockerfile              # Container image
  AGENTS.md               # AI coding agent instructions (plus tests/, terraform/, .github/workflows/)
  README.md               # Main documentation

    Note

    Claude Code skips AGENTS.md when a CLAUDE.md, .claude/CLAUDE.md, or CLAUDE.local.md sits in your working directory or above it, and on older versions. See When AGENTS.md support is unavailable for the version floor and the setting that keeps a personal CLAUDE.local.md alongside it.
