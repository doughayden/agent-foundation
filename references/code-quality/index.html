    Code Quality

    Detailed code quality tools, enforcement strategies, and exclusion guidelines.

    Overview

    Tools to enforce code quality:
    1. Ruff - Fast linting and formatting (replaces flake8, isort, black)
    2. Mypy - Static type checking
    3. Pytest - Testing with coverage

    All configured in pyproject.toml.

    Note

    THIS GUIDE IS A TEMPLATE
    Replace {your_agent} found throughout the guide with your package name (e.g., my_custom_agent)

    Running Quality Checks

    Each tool, in suite order:

    # Lint with ruff auto-fix first (security, bugs, style violations)
uv run ruff check --fix

# Then format, so the formatter sees the auto-fixed code
uv run ruff format

# Type check
uv run mypy

# Tests with coverage
uv run pytest --cov

    On every commit: once installed (uv run pre-commit install), the hooks in .pre-commit-config.yaml run the lint, format, and type-check tools above in this order on the staged files, plus any other checks the config defines. CI runs the same hooks over the whole tree, which you can reproduce on demand:

    uv run pre-commit run --all-files

    Before pushing: run the tests, which the hooks do not:

    uv run pytest --cov

    Plus any other test lanes the project defines, like integration tests.

    Order matters: everything that rewrites files finishes before anything that only reads them. ruff check --fix can change layout the formatter must then normalize, and mypy should check the final source. pyproject.toml does not set ruff's fix = true, so a bare ruff check (no --fix) only reports.

    Ruff Configuration

    What We Enforce

    From pyproject.toml:

    [tool.ruff.lint]
select = [
    "E",   # pycodestyle errors (PEP 8 violations)
    "W",   # pycodestyle warnings
    "F",   # pyflakes (unused imports, undefined names)
    "I",   # isort (import sorting)
    "B",   # flake8-bugbear (common bugs and design problems)
    "C4",  # flake8-comprehensions (better list/dict comprehensions)
    "UP",  # pyupgrade (modern Python syntax)
    "N",   # pep8-naming (naming conventions)
    "S",   # flake8-bandit (security issues)
    "SIM", # flake8-simplify (code simplification)
    "PTH", # flake8-use-pathlib (use Path instead of os.path)
]

    Key enforcements:
    - E501: Line too long (88 characters)
    - PTH (pathlib rules): Use pathlib.Path instead of os.path
    - PTH123: Use Path.open() instead of open()
    - PTH118: Use Path.joinpath() instead of os.path.join()
    - Why: Modern API, cross-platform, chainable (path / "subdir"), type-safe
    - Ruff auto-fixes many os.path calls to Path
    - S (security rules): Catch common security issues
    - S101: Use of assert (banned in production, allowed in tests via per-file ignore)
    - S104: Binding to 0.0.0.0 (flagged for security, intentional in containers)
    - S105: Possible hardcoded password (detects patterns like "password = 'secret'")

    Per-file Exclusions

    From pyproject.toml:

    [tool.ruff.lint.per-file-ignores]
"tests/**/*.py" = ["S101"]  # Allow assert statements in tests

    Why: Tests use assert for validation. This is standard pytest practice and not a security concern.

    Inline Exclusions

    Real example from our codebase:

    # tests/unit/conftest.py
mock_credentials.token = "test-mock-token-totally-not-real"  # noqa: S105

    Rule: S105 (Possible hardcoded password)
    Why excluded: This is a test mock credential, not a real secret. The string content makes it obvious it's not production.

    Real example from tests:

    # tests/unit/test_config.py
"HOST": "0.0.0.0",  # noqa: S104

    Rule: S104 (Binding to all interfaces)
    Why excluded: Docker containers need to bind to 0.0.0.0 to accept connections from the host. This is intentional and documented.

    When to use # noqa:
    - Security rules (S*) with false positives on test code
    - Line length (E501) for URLs or data that can't be split
    - Specific rule violation that's intentional and safe

    Prefer specific rule codes:

    # Good - clear what's being suppressed
url = "https://example.com/very/long/api/path"  # noqa: E501

# Avoid - unclear what's being allowed
some_code()  # noqa

    Use # noqa only when:
    - Rule violation is intentional and well-justified
    - Auto-fix would make code less readable
    - External constraint prevents compliance (e.g., third-party API format)

    Ruff Auto-fix

    Ruff can automatically fix many issues:

    # Auto-fix all fixable issues
uv run ruff check --fix

# Preview fixes without applying (safe mode)
uv run ruff check --diff

    What gets auto-fixed:
    - Import sorting (rule I)
    - Unused imports (rule F401)
    - Whitespace and indentation (rules E, W)
    - Quote style normalization (rules Q)
    - Trailing commas (rules COM)
    - Simple code transformations (e.g., os.path.join() → Path.joinpath())

    What requires manual fixing:
    - Complex logic issues
    - Security concerns (rule S)
    - Naming violations (rule N)
    - Code simplification requiring logic changes (rule SIM)

    Best practice:
    1. Run uv run ruff check --fix first (auto-fixes linting issues)
    2. Run uv run ruff format second (formats the fixed code)
    3. Review remaining issues and fix manually

    Mypy Configuration

    What We Enforce

    From pyproject.toml:

    [tool.mypy]
plugins = ["pydantic.mypy"]
python_version = "X.Y"  # follows .python-version
# Tests are namespace packages (no __init__.py), so module names come from paths
explicit_package_bases = true
mypy_path = "src"
files = ["src", "tests"]
strict = true
warn_unused_configs = true
warn_unreachable = true

    strict = true turns on mypy's maintained strict flag set, and picks up new checks as mypy adds them to it. See --strict for the current list. warn_unreachable sits outside that set, so it is enabled on its own. The pydantic plugin checks model construction, like ServerEnv(...), against the declared field types.

    Key enforcements:
    - Every function needs complete annotations (args + return)
    - def foo(x: str = None) is an error (must use str | None)
    - Returning Any from a typed function is flagged (type safety leak)
    - if my_str == 5: is an error (comparing incompatible types)
    - Unused # type: ignore comments and redundant casts are errors
    - Names imported from a package that does not explicitly re-export them are errors (no_implicit_reexport). Import from the defining submodule instead, like google.adk.tools.function_tool rather than google.adk.tools
    - Dead code after returns/raises is flagged (warn_unreachable)

    Example Errors and Fixes

    Error: missing return annotation (no-untyped-def)

    # mypy error: Function is missing a return type annotation
def process_data(items: list[str]):
    return len(items)


# Fixed
def process_data(items: list[str]) -> int:
    return len(items)

    Error: partially annotated function (no-untyped-def)

    # mypy error: Function is missing a type annotation for one or more arguments
def fetch_user(id: int, cache):
    return cache.get(id)


# Fixed
def fetch_user(id: int, cache: dict[int, User]) -> User | None:
    return cache.get(id)

    Error: implicit None default (assignment)

    # mypy error: Incompatible default for argument (expected str, got None)
def greet(name: str = None) -> str:
    return f"Hello, {name or 'stranger'}"


# Fixed - explicit None in union
def greet(name: str | None = None) -> str:
    return f"Hello, {name or 'stranger'}"

    Test Suite Typing Strategy

    mypy checks tests/ alongside src/, with two overrides:

    [[tool.mypy.overrides]]
# Test functions take fixtures by name without annotations
module = "tests.*"
disable_error_code = ["arg-type", "no-untyped-def", "no-untyped-call"]

[[tool.mypy.overrides]]
# Fixture definitions stay fully typed
module = "tests.*.conftest"
enable_error_code = ["no-untyped-def", "no-untyped-call"]
    Disabled code Why
    no-untyped-def pytest injects fixture parameters by name, not by type. Annotating test function parameters adds ceremony without signal.
    no-untyped-call Follows from the above: calling an unannotated test helper from a typed function.
    arg-type Duck-typed mocks (like MockMemoryCallbackContext) intentionally stand in for real types in tests.

    Every other strict check applies to tests. The second override re-enables the annotation checks for conftest.py files, so fixture definitions carry full annotations (MockerFixture in, MockType out) and an unannotated fixture fails mypy. It must use enable_error_code: a narrower section's disable_error_code does not undo codes a broader matching section disabled.

    @pytest.fixture
def mock_state(mocker: MockerFixture) -> MockType:
    """Mock state with test data."""
    state: MockType = mocker.Mock(spec=State)
    return state

    Patterns the strict checks shape in tests:
    - Annotate a mocker.Mock(...) result before returning it. mypy infers it as Any, so a direct return mocker.Mock(...) from a -> MockType fixture fails no-any-return.
    - Call a -> None function without capturing its result. result = callback(...); assert result is None fails func-returns-value, and mypy already proves the None return from the signature.
    - Patch a module attribute with mocker.patch.object(module, "name", ...), not module.name = value. Assignment to a name the module does not re-export fails attr-defined; the string form also restores the original on teardown. Session-scoped fixtures use pytest-mock's session_mocker.
    - Narrow parsed data with isinstance() before returning it as a concrete type. yaml.safe_load and json.loads return Any.
    - Third-party packages without type information get a narrow ignore_missing_imports override in pyproject.toml, with a comment naming why. Check first whether a newer release or a stub package (types-*) supplies types.

    Inline Exclusions

    When you might need # type: ignore:

    # Third-party library without type stubs
import untyped_library  # type: ignore[import-untyped]

# Mypy bug or limitation (add TODO)
result = complex_function()  # type: ignore[return-value]  # TODO: Fix when mypy supports this pattern

    Always prefer:
    1. Fix the actual type issue (restructure code to make types clear)
    2. Add type stubs for third-party libraries
    3. Use type narrowing - validate types at runtime with isinstance() checks or type guards

    Never use cast() - use type narrowing instead:

    Why cast() is bad:
    - Bypasses type safety: Tells mypy to trust you without verification
    - Runtime risk: No runtime validation - type mismatch crashes at runtime
    - Dishonest about code behavior: Hides the actual types being used
    - Maintenance burden: Future changes break assumptions silently

    Type narrowing is always better:

    # Bad - using cast() (DON'T DO THIS)
from typing import cast

result = some_function()
value = cast(str, result)  # Trust me, it's a string! (no runtime check)

# Good - type narrowing with isinstance()
result = some_function()
if not isinstance(result, str):
    raise TypeError(f"Expected str, got {type(result)}")
value = result  # mypy knows this is str now, AND we validated at runtime

    Type narrowing keeps you honest about what the code actually does - it satisfies both mypy and provides runtime safety.

    Workflow Lint and Version Pins

    actionlint runs only as a pre-commit hook, so its rev in .pre-commit-config.yaml is the single version pin and CI enforces it through the code-quality pre-commit step, with no separate job or Docker image. actionlint also runs shellcheck over inline run: blocks, but only when shellcheck is on PATH. The CI runner always has it, so CI's result is deterministic; a machine without it skips the pass, and its findings surface only in CI. Quote expansions (SC2086) and group consecutive appends to one file into { ...; } >> "$FILE" (SC2129); where grouping would hurt readability, use a # shellcheck disable=SC2129 on that one command with the reason beside it, never a file-wide directive. zizmor (template injection, unpinned actions, excessive permissions) is a separate audit with its own findings and is not part of the actionlint hook.

    Terraform is pinned once, in .terraform-version (exact X.Y.Z). tenv reads it locally. hashicorp/setup-terraform has no version-file input, so each workflow step that installs Terraform is preceded by a step that reads the file into an output. TestTerraformVersionPin in tests/unit/test_pinned_versions.py fails if a workflow hard-codes terraform_version. Each root's required_version stays a range.

    Coverage Configuration

    What We Enforce

    From pyproject.toml:

    [tool.coverage.run]
source = ["src"]
branch = true  # Check both line and branch coverage

[tool.coverage.report]
fail_under = 100  # Require 100% coverage

    100% coverage is non-negotiable for production code.

    File-level Exclusions

    From pyproject.toml:

    [tool.coverage.run]
omit = [
    # server.py: wiring run at import (settings, telemetry, ADK app); smoke lane
    "src/**/server.py",
    # agent.py: App and LlmAgent composition; eval lane
    "src/**/agent.py",
]

    A file is omitted only when it is wiring with no logic of its own and another test lane runs it for real. Each comment names that lane:
    - server.py: builds the app at import, after settings and telemetry setup. The smoke lane exercises it on the deployed service; a unit test would only re-check the wiring with every dependency mocked.
    - agent.py: composes the App and LlmAgent. The eval lane runs it against a real model.

    Everything else is measured, including __init__.py (its PEP 562 lazy loader is real branching logic) and prompt.py. Pattern: test every new file; omit one only when it meets the same bar, and name the lane in its comment.

    Line-pattern Exclusions

    When a measured file gains lines that never run under test, exclude those lines by pattern instead of omitting the file. Add the pattern to [tool.coverage.report] exclude_also in pyproject.toml when the code first appears. Common patterns:

    [tool.coverage.report]
exclude_also = [
    'if __name__ == "__main__":',  # script guard
    "if TYPE_CHECKING:",           # type-checker-only imports
    "@overload",                   # typing overload stubs
    "raise NotImplementedError",   # abstract method bodies
]

    The template sets none today: no measured file contains these lines. See coverage.py: Excluding code.

    Inline Exclusions

    Real example from our codebase:

    # src/{your_agent}/config.py (ServerEnv.allow_origins_list)
if not isinstance(result, list):  # pragma: no cover
    # Pydantic validation makes this unreachable
    msg = "Invalid allow_origins format"
    raise TypeError(msg)

    Why: The @field_validator above this property ensures result is always a list. This defensive check exists for static type safety but is unreachable at runtime. Pydantic guarantees it.

    When to use # pragma: no cover:
    - Defensive code (provably unreachable) needed to satisfy the static type-checker
    - Platform-specific branches not testable in CI (e.g., Windows-only code)
    - Error paths that require external system failures (rare)

    When NOT to use it:
    - "This is hard to test" - write better tests or use better code patterns to facilitate testing
    - "Coverage is annoying" - coverage is finding gaps as intended
    - Normal error handling - always test error paths

    Workflow Integration

    When to Run Checks

    On every commit: the pre-commit hooks run lint, format, and type checks automatically.

    Before pushing: uv run pytest --cov, plus any other test lanes the project defines.

    During development:
    - Run ruff check --fix and ruff format frequently as you code
    - Run mypy after adding new functions or changing signatures
    - Run tests after behavior changes

    IDE Integration:
    - Configure your editor to run ruff format on save
    - Enable mypy real-time checking for immediate feedback
    - Use pytest plugin for test execution and debugging

    CI Enforcement:
    All checks run automatically in GitHub Actions on every PR:
    - Code quality workflow runs ruff, mypy, pytest
    - Blocks merge if any check fails
    - Ensures main branch always passes quality gates

    Philosophy

    Why These Standards?

    Strict typing (mypy):
    - Catch bugs before runtime
    - Enable powerful IDE features
    - Document code contracts
    - Facilitate safe refactoring

    100% coverage:
    - Confidence in changes
    - Forces thinking about edge cases
    - Documents all code paths
    - Prevents untested code accumulation

    Automated formatting (ruff):
    - Eliminates style debates
    - Consistent codebase
    - Fast code review
    - Auto-fix reduces friction

    Security checks (bandit via ruff):
    - Catch common security mistakes
    - Enforce safe defaults
    - Educate developers on risks

    When to Add Exclusions

    Never add exclusions:
    - To make broken code pass checks
    - Because it's "too much work"
    - For personal style preference
    - To ship faster without fixing issues

    Acceptable exclusions:
    - Third-party library limitations (document why, add TODO if fixable)
    - Tool bugs (add TODO to fix when tool updates)
    - Provably unreachable defensive code (rare, requires strong justification)
    - Test-specific patterns (e.g., assert in tests, mock credentials)

    Best practices:
    1. Be specific: Use rule codes (# noqa: S105) not blanket suppression (# noqa)
    2. Document why: Add comment explaining the exclusion
    3. Add TODOs: If it's a workaround, plan to fix it later
    4. Review regularly: Remove exclusions when underlying issue is fixed

    Always prefer fixing the issue over adding exclusions.
